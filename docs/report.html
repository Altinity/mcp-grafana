Grafana + MCP Integration:
Per-User Identity Architecture

Technical Report · Proof of Concept · demo.altinity.cloud

2026-05-20 POC Complete ClickHouse 26.1.x Grafana 12.4.3 MCP / CIMD

Executive Summary

Altinity completed a proof-of-concept demonstrating that AI assistant clients (claude.ai, ChatGPT) can query company ClickHouse data with full per-user identity propagation — every query carries the authenticated user's JWT so that ClickHouse RBAC knows exactly who ran it, producing a verifiable audit trail in system.query_log.

The integration runs on the demo.altinity.cloud Kubernetes cluster and threads together Google OAuth, Rauthy (OIDC broker), Grafana 12.4.3, a forked mcp-grafana broker, and two ClickHouse clusters. The critical insight was that Google issues opaque access tokens — not JWTs — so a Rauthy broker layer is required to produce the RS256 JWTs that ClickHouse's token processor expects.

The result: calling query_clickhouse(datasource="otel", query="SELECT currentUser()") from claude.ai returns btyshkevich@altinity.com, confirmed in ClickHouse query logs. The architecture is extensible to production with PVC-backed storage, row-level security, and DCR-based client registration.

Update — 2026-05-20 (round 2): Resolved a previously-hidden collision between auth.jwt (used by mcp-grafana) and auth.generic_oauth (browser users) that flipped user_auth.auth_module to jwt for shared users and silently disabled oauthPassThru on browser-side dashboard queries. Fix is config-only: enable Grafana's improvedExternalSessionHandling feature toggle, which moves OAuth tokens into a per-session user_external_session table instead of the most-recent-row-wins user_auth table. Both paths now coexist for the same user. Separately, fixed a dashboard JSON case-sensitivity bug where uppercase "format": "TABLE" in the new claude-usage-reporting dashboard caused all stat panels to render empty.

Key Problems SolvedEngineering challenges encountered and resolved during the POC

🔌
Official Grafana ClickHouse plugin doesn't support per-user OAuth

grafana-clickhouse-datasource is a Go backend plugin that opens its own CH connection at registration time — before any user request. forwardOAuthIdentity is advertised but a silent no-op in the actual code path.

Solution
Use vertamedia-clickhouse-datasource which uses access: proxy mode. Grafana core adds the OAuth header — not the plugin — so per-user tokens propagate correctly.
🔑
Google issues opaque access tokens, not JWTs

ClickHouse's <token_processor type=openid> requires a signed JWT with verifiable claims. Grafana's oauthPassThru would forward an opaque ya29.… blob; ClickHouse rejects it with "Code 1001: invalid token supplied".

Solution
Introduce Rauthy as an OIDC broker upstream of Google. Users authenticate via Google but Rauthy issues its own RS256 JWT access tokens — proper JWTs that CH's token processor can validate.
🔗
auth.jwt sessions don't create OAuth sessions

mcp-grafana authenticates via X-JWT-Assertion header. Grafana's auth.jwt validates and resolves the user — but does NOT mint an OAuth session. So oauthPassThru has nothing to forward, sending user=default and causing CH to throw "Bad cast from BasicCredentials to TokenCredentials".

Solution
The vertamedia adapter in mcp-grafana bypasses Grafana's proxy entirely and calls CH directly, reading the JWT from cfg.JWTAssertion in the MCP broker context. No Grafana OAuth session required.
🔐
Google JWTs rejected by rauthy_oauth on otel CH

Initial design used Google as the mcp-grafana OAuth upstream. The bearer token was a Google id_token. The otel CH cluster has a rauthy_oauth processor keyed to Rauthy's JWKS — no Google keys there — producing "Code 516: JWKS error: no JWK found for JWT".

Solution
Switch mcp-grafana's OAuth upstream to Rauthy. The token type matches the browser user path — both receive Rauthy RS256 JWTs, and the otel CH processor validates both identically.
⚙️
Single <token> constraint in ClickHouse 26.1.x

Attempted to configure two <token> entries (google_oauth + rauthy_oauth) on antalya CH 26.1.11. First attempts on 26.1.6 produced "Code 318: Only one token section can be defined". On 26.1.11 the config loaded but broke Google id_token logins — order-sensitivity in user_directories.xml.

Partial Solution / Status
For otel CH: replaced google_oauth with rauthy_oauth only (decommissioned otel-google-mcp). For antalya CH: reverted on 2026-05-19; needs deeper investigation before re-attempting. Pending fix.
🪢
auth.jwt and oauthPassThru collide on shared users

With both auth.jwt (for mcp-grafana) and auth.generic_oauth (for browser users) enabled and matched to the same Grafana user by email, every mcp-grafana hop writes a new user_auth(user_id, auth_module='jwt') row. Grafana's oauthtoken middleware then reads back the single most-recent user_auth row via GetAuthInfo and gates on HasPrefix(authmodule, "oauth_") — the jwt row clears the gate FALSE, the browser's data-proxy hop to CH goes out without a Bearer, CH falls back to default → "Code 194: REQUIRED_PASSWORD", panels go blank.

Solution (config-only, 2026-05-20)
Enable Grafana's improvedExternalSessionHandling feature toggle. OAuth tokens migrate from user_auth.oauth_token (most-recent-wins) into a per-session user_external_session table; the middleware now reads the session-scoped row, so the two auth modules stop colliding. Migration gotcha: existing logged-in users must re-login once after enabling the flag so a user_external_session row is minted for their cookie — until then they still hit the old gate.
🔤
Stat panels showed "No data" even though queries succeeded

The claude-usage-reporting dashboard's Executive Summary KPI panels (stat type, format: "TABLE") returned valid single-row results from CH but rendered empty. Inspect → Data showed rows: 1 in the response, but the panel reduce-op (lastNotNull) found nothing. Root cause: the dashboard JSON used uppercase "TABLE" / "TIME_SERIES" (legacy Grafana constants); the vertamedia plugin's response dispatcher in src/datasource/datasource.ts:404 does target.format === 'table' case-sensitively. Every stat target fell through to the timeseries branch, which expects a timestamp column, producing empty frames.

Solution
Patch the dashboard JSON via Grafana's admin API to lowercase all target.format values. The Grafana UI normalises new edits to lowercase, but it does NOT retroactively fix existing JSON — exports from other tools or hand-written dashboards routinely use the uppercase legacy form, which silently breaks stat panels.

Known Issues & Potential DrawbacksItems requiring attention before production use

  • 1
    antalya CH: mcp-grafana query_clickhouse fails HIGH

    antalya CH currently has only google_oauth token processor; mcp-grafana now sends Rauthy RS256 JWTs. The rauthy_oauth entry was rolled back on 2026-05-19 after it broke Google id_token logins. Root cause: order-sensitivity in <user_directories> loading under ClickHouse 26.1.x — both entries share the same internal load path and the second clobbers something. Requires deeper investigation before re-attempting the two-token configuration.

  • 2
    User-created dashboards live only in Grafana's unified storage MEDIUM

    persistence.enabled: true (PVC grafana, 1Gi) so user dashboards survive pod restarts. However the claude-usage-reporting dashboard was created interactively and lives only in Grafana's unified storage (sqlite resource table on the PVC) — not in any ConfigMap. A cluster rebuild or PVC deletion wipes it. Provisioned dashboards (token-usage, antalya-quickstart) come back on startup from the grafana-dashboards-default ConfigMap. To preserve interactively-built dashboards across rebuilds, dump them via the admin API and check them into deploy/grafana/.

  • 3
    Single-tenant MCP broker — no Dynamic Client Registration (DCR) MEDIUM

    The mcp-grafana CIMD-only broker does not support DCR (RFC 7591). AI clients must be pre-configured with the connector URL. Adding a new AI client (e.g. ChatGPT, a custom MCP client) requires manual registration in both Rauthy (new OIDC client) and mcp-grafana config. Not scalable for broad deployment.

  • 4
    Rauthy ephemeral PVC — sessions and secrets lost on PVC removal MEDIUM

    Rauthy uses a PVC for persistence. If the PVC is deleted (cluster teardown, accidental removal), all active sessions, refresh tokens, and Rauthy-managed client secrets are gone. ENC_KEYS (used for JWE) must be backed up separately. The bootstrap flow — re-creating OIDC clients, re-registering connectors — is currently manual.

  • 5
    No row-level security — all authenticated users can read all otel data MEDIUM

    Per-user CH identity is proven, but the oauth_otel_role grants SELECT ON claude_otel.* to any authenticated user. Every user with a valid Rauthy JWT can read all Claude API telemetry regardless of whose data it is. This is acceptable for internal tooling where all users are trusted, but is not suitable for multi-tenant or customer-facing deployments.

  • 6
    Token lifetime gap — MCP sessions expire if Rauthy is down during refresh LOW

    Rauthy access tokens default to 30 minutes. MCP_OAUTH_UPSTREAM_OFFLINE_ACCESS=true enables refresh token flow, but if Rauthy is unavailable during a refresh window, MCP sessions expire and users must re-authenticate. Google id_tokens (antalya-mcp path) have similar ~1h lifetime. Not a blocking issue for demo, but worth noting for production SLA planning.

  • 7
    vertamedia plugin: JS frontend bypasses its own Go backend LOW

    Even though plugin.json declares "backend": true, the plugin's JavaScript overrides query() at src/datasource/datasource.ts:519 and routes every panel query through Grafana's data-proxy (/api/datasources/proxy/uid/<uid>) instead of the Go QueryData handler. The Go backend is only invoked for resource calls (variable population, health). Patching the Go binary cannot affect dashboard panels — anything attempted there has to survive Grafana's proxy auth middleware. This is why the proxy-side oauthPassThru path has to be sound for dashboards to render at all.

  • 8
    Plugin must be loaded via GF_PLUGINS_ALLOW_LOADING_UNSIGNED_PLUGINS LOW

    vertamedia-clickhouse-datasource is community-signed; the env flag relaxes signature checking. The official Grafana ClickHouse plugin doesn't propagate per-user identity (see Problems Solved #1), so there's no signed alternative. If a binary is ever hot-patched in-pod for diagnosis, Grafana re-downloads the signed v3.4.11 from GF_INSTALL_PLUGINS on next restart unless MANIFEST.txt is deleted first (signature switches from "modified" to "unsigned-allowed").

  • 9
    Dashboard JSON target.format must be lowercase LOW

    vertamedia's response dispatcher compares target.format against the literals 'table' / 'time_series' with ===. Dashboard JSON exported from other tools or hand-written using legacy Grafana constants stores "TABLE" / "TIME_SERIES" (uppercase); the comparison silently fails, all targets fall through to the timeseries branch, and stat panels show "No data" while every other panel type may render correctly. Any new dashboard imported into this Grafana needs to be lowercase-normalised — the Grafana UI does it for fresh edits, not retroactively. Worth wiring a lint/precommit hook if dashboards are versioned in Git.

  • 10
    CH 26.1+ rejects sum(col) AS col aliasing LOW

    CH 26.1+ resolves an alias inside later aggregate arguments in the same SELECT, so sum(input_tokens) AS input_tokens, sum(input_tokens + output_tokens) ... is read as sum(sum(input_tokens) + ...) and throws "Code 184: ILLEGAL_AGGREGATION". Caught the Per-user reporting table panel on claude-usage-reporting; the table panel returns 500 even when the rest of the dashboard renders fine. Fix is mechanical (rename aliases to distinct identifiers, e.g. AS inputs) but not yet applied to this dashboard — left as a follow-up.

Why We Forked mcp-grafana & What We Contributed BackUpstream project gaps, design rationale, and open pull requests

Background: upstream mcp-grafana

grafana/mcp-grafana is the official Grafana MCP server. It exposes Grafana capabilities (dashboard search, datasource queries, alerting, etc.) to AI assistants via the Model Context Protocol. Out of the box it authenticates to Grafana using a static service account token — a single shared identity, with no way to propagate the end-user's identity through to downstream data sources.

Two capabilities were missing that are required for the Altinity use-case:

  1. An OAuth broker that performs CIMD-only forward-mode auth so claude.ai / ChatGPT can authenticate users without requiring Dynamic Client Registration (DCR). Without this, AI clients cannot obtain a per-user bearer token at all.
  2. Per-user ClickHouse queries against the vertamedia datasource type, calling ClickHouse directly with the authenticated user's JWT rather than routing through Grafana's datasource proxy (which cannot forward the JWT in the auth.jwt session path).

Rather than waiting for upstream to add these features, Altinity forked the repository and implemented both capabilities as self-contained additions with minimal changes to the upstream codebase. The work is split into two pull requests against the Altinity fork, structured so they can be proposed back to the upstream project independently.

PR #1 OAuth Broker — build infra + OAuth wiring

Adds the full CIMD-only OAuth forward-mode broker built on github.com/BorisTyshkevich/go-mcp-oauth. Wires the broker into cmd/mcp-grafana/main.go behind a CLI flag (--oauth-enabled), mounts the broker's HTTP handlers on the same mux as the MCP endpoint, and exposes a PropagateIdentity context-func that copies the validated bearer from the broker's request context into GrafanaConfig.JWTAssertion. The JWTAssertionRoundTripper then adds X-JWT-Assertion: <token> to every outbound Grafana API call so auth.jwt resolves the user.

Deep Dive: Why vertamedia works but the official ClickHouse plugin cannot

❌ grafana-clickhouse-datasource (official)

A Go backend plugin. Grafana loads it as a subprocess and calls its Connect() handler at plugin registration time — before any user ever makes a request. The plugin opens a long-lived ClickHouse TCP/HTTP connection using whatever credentials are in the datasource config (username/password or no-auth). All subsequent user queries reuse that pooled connection.

The plugin does advertise a forwardOAuthIdentity flag in its JSON schema, but inspection of the plugin source up to v4.17.0 finds zero references to oauthPassThru, Authorization header injection, or X-Id-Token handling in the query path. The flag is silently ignored.

Even if the flag were honoured, the plugin has no access to the current HTTP request context (and therefore no OAuth session token) at query time — the architecture does not allow it.

✅ vertamedia-clickhouse-datasource

A frontend-only plugin. It does not open any connection itself. Instead it configures the datasource with access: proxy, which means Grafana core's own HTTP reverse-proxy handles every panel query: it builds the outbound request to ClickHouse's HTTP interface, and — crucially — when oauthPassThru: true is set it injects Authorization: Bearer <access_token> from the active OAuth session before forwarding.

This means the plugin code is entirely out of the auth path. Per-user identity works for any datasource with access: proxy and an active auth.generic_oauth session — the plugin just needs to format its queries as HTTP GET/POST to ClickHouse's JSON API, which vertamedia does.

The Altinity oauth-examples repository independently confirms this architecture is the correct approach for per-user CH identity from Grafana.

⚠ Remaining gap: auth.jwt sessions do not produce OAuth tokens

Even with vertamedia, oauthPassThru only works when the user has an auth.generic_oauth session (the Rauthy login flow in a browser). When mcp-grafana authenticates via X-JWT-Assertion, Grafana's auth.jwt subsystem resolves the user but does not mint an OAuth session — so oauthPassThru finds no token to forward and Grafana sends unauthenticated requests to CH (user=default), which CH rejects.

Solution (PR #2): the vertamedia adapter in mcp-grafana bypasses Grafana's proxy entirely. It reads ds.URL from the datasource model (still fetched via Grafana API, preserving the RBAC visibility gate) and calls ClickHouse directly with Authorization: Bearer <cfg.JWTAssertion>. ClickHouse's own JWKS-based token processor validates the JWT — exactly the same validation it would have run on a Grafana-forwarded copy. Net auth posture: identical. Code complexity: minimal.

Upstream contribution path

PR #1 (OAuth broker) is a general-purpose feature with no Altinity-specific code and is a strong candidate for upstream acceptance. PR #2 (vertamedia adapter) adds support for a specific community plugin and calls CH outside Grafana's proxy — this is a deliberate divergence that upstream may not want to merge, but it is kept in a separate file (tools/clickhouse_vertamedia.go) so it does not interfere with the official CH datasource path and can be maintained as a long-lived fork patch with minimal merge friction.
