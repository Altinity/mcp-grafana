Reading from ClickHouse — browser path

This is what happens when you open the Claude API — Token Usage dashboard in a tab. It's the path that works today, and it's why the issue was easy to miss until the MCP path got tested.

Figure 1 — Dashboard rendering. Grafana mints a session from the cookie, looks up the upstream OAuth token attached to that session, forwards it as Authorization on the proxied request.

The URIs

#MethodURIAuth
1GEThttps://grafana-oauth.demo.altinity.cloud/api/datasources/proxy/uid/otel/?query=…+FORMAT+JSON&database=claude_otelcookie grafana_session=…
2(in-process) Grafana's datasource-proxy handler resolves the user from the cookie, fetches the upstream OAuth token from session storage, and prepares the outbound CH request.
3GEThttp://clickhouse-otel.demo.svc.cluster.local:8123/?query=…+FORMAT+JSON&database=claude_oteluser JWT Authorization: Bearer ⟨jwt⟩
Why it works: the cookie path establishes a real Grafana OAuth session at login. Step 2 has a token to forward. oauthPassThru=true on the datasource tells Grafana do forward it.

Reading from ClickHouse — MCP path

This is the path that PR #2 fixes. Two key differences from the browser path: there's an extra hop (mcp-grafana sits between claude.ai and Grafana), and the user identity arrives as X-JWT-Assertion instead of a cookie — which turns out to be the decisive difference.

Figure 2 — MCP query flow. Discovery still goes through Grafana (for the datasource model + RBAC gate); the query itself talks to ClickHouse directly with the user's own JWT.

The URIs

#MethodURIAuth
1POSThttps://mcp-grafana.demo.altinity.cloud/mcp (MCP tools/call query_clickhouse)user JWT Authorization: Bearer ⟨jwt⟩
—Broker validates the bearer against the upstream IdP's JWKS, applies --oauth-required-scopes / --oauth-allowed-email-domains, and stores the raw JWT on ctx.GrafanaConfig.JWTAssertion.
2GEThttps://grafana-oauth.demo.altinity.cloud/api/datasources/uid/otel — discovery + RBAC gateSA Authorization: Bearer ⟨SA_token⟩ & user JWT X-JWT-Assertion: ⟨jwt⟩
3Grafana [auth.jwt] resolves the user from X-JWT-Assertion, checks datasources:read permission, returns the datasource model with url, jsonData.defaultDatabase, etc.
4GEThttp://clickhouse-otel.demo.svc.cluster.local:8123/?query=…+FORMAT+JSON&database=claude_oteluser JWT Authorization: Bearer ⟨jwt⟩
5ClickHouse's token_processor validates the JWT against the configured JWKS, maps it to a CH user (typically by the email claim), runs the query as that user.
Why we don't route step 4 through Grafana's proxy: Grafana's oauthPassThru only forwards a token when the user has a Grafana-managed OAuth session. The browser path establishes one at OAuth login (stored against the grafana_session cookie). The MCP path arrives via X-JWT-Assertion → [auth.jwt], which resolves the user but does not mint a session. So oauthPassThru has nothing to forward, and proxied CH queries fall back to whatever credentials the datasource has configured (or fail). Same identity material, different last-hop arrangement — and Grafana's auth subsystems don't compose across that boundary.
Net authentication posture vs the dashboard path: identical. ClickHouse runs the same JWKS validation in both cases; only the courier changes. We trade one cleanly-typed Grafana hop for direct CH access, gaining latency and reliability without weakening identity.

Why we still call Grafana at all

Step 2 isn't load-bearing for auth — ClickHouse will validate the JWT regardless. It serves three other purposes:

  • Configuration registry. The CH URL, the default database, TLS settings — they all live on the Grafana datasource model. Reading ds.URL means the adapter stays portable: anyone configuring a vertamedia datasource in Grafana already supplies it.
  • RBAC gate. The calling user must be permitted to see the datasource via Grafana's permission model. Drop this check and any holder of a valid JWT can query any CH that mcp-grafana knows about.
  • Discovery uniformity. Same getDatasourceByUID call as every other datasource-bound tool in mcp-grafana. The dispatch in newClickHouseClient is the only place that branches on plugin type.

Why the asymmetry: Grafana writes go through, ClickHouse reads bypass

It's worth being explicit about why we kept Grafana on the path for dashboard writes but dropped it for CH queries — they look superficially similar but they're not.

Dashboard writeClickHouse read
System of recordGrafanaClickHouse
RBAC ownerGrafana — dashboards:writeClickHouse — JWT subject mapping + CH grants
Identity carrierX-JWT-Assertion resolved by Grafana [auth.jwt]Authorization: Bearer validated by CH JWKS
Does Grafana need to forward identity onward?No — Grafana is the destinationYes — but it can't (no OAuth session under auth.jwt)

For dashboard writes, Grafana itself is the system that needs to know the user — so the X-JWT-Assertion mechanism is sufficient and the request stops there. For CH reads, Grafana would have been an intermediary that has to forward identity to another system, and the only Grafana feature that does that (oauthPassThru) doesn't compose with the auth.jwt identity source. So we route around it.
